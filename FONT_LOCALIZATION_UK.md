# LOTR: The Return of the King (2003, EA) — українська локалізація шрифтів/тексту

Робочий довідник для продовження патчингу кириличних/українських шрифтів для PC-версії
*The Lord of the Rings: The Return of the King* (EA Redwood Shores, 2003).

Використана інсталяція гри: `C:\Program Files (x86)\Return of the King\` (російська
локалізована версія, використовується як база для всіх збірок — її кириличні гліфи для
кодів 192-255 вже коректно рендеряться в грі). Також є чиста англійська інсталяція
`C:\Program Files (x86)\EA GAMES\LOTR - The Return of the King ENG\` (використовувалась
один раз — щоб порівняти, що оригінально лежало в слотах 165-191).

## 1. Формат контейнера `.scw`

Кожен `.scw`-файл (і локалізаційний архів `GlobScen.scw`, і поаудмісні архіви на кшталт
`cra01.scw`) використовує **однаковий кастомний чанковий контейнер**. Тепер це
реалізовано, задокументовано по кожному полю і перевірено побайтово у **`lotr_scw_tool.py`**
(цей репозиторій) — вважай цей файл авторитетним джерелом, а не текст нижче (він лишений
тут як короткий підсумок; якщо вони розійдуться — довіряй коду та його ж докстрингу, який
звірявся з декомпіляцією реального опенсорсного інструменту **Game Extractor**, клас
`org.watto.ge.plugin.archive.Plugin_SCW`):

- Теги чанків зберігаються на диску **у зворотному порядку байтів**. Приклади: сирі байти
  `COHS` на диску = `SHOC`, якщо читати вперед; `RDHS` = `SHDR`; `LLIF` = `FILL`;
  `LRTC` = `CTRL`; `ONOS` = `SONO`.
- Заголовок чанка = 4-байтний перевернутий тег + 4-байтна довжина (little-endian), довжина
  **включає** сам 8-байтний заголовок (тобто "наступний чанк починається за адресою
  `this_offset + length`").
- Усередині чанка `COHS`/`ONOS`, зміщення байтів **відносно самого тегу чанка**:
  `[8:16)` — 8 зарезервованих байт, `[16:20)` — тег "file header" (`RDHS`=SHDR /
  `TADS`=SDAT / `tadR`=Rdat/стиснуто). Саме для `SHDR`-чанка: `[24:28)` = `ext`
  (перевернуто, напр. `"font"`, `"subT"`), `[32:36)` = `decompLen` (little-endian u32,
  загальний декомпресований розмір ресурсу по всьому ланцюжку чанків). **У попередній
  версії цього розділу тег file-header був зміщений на 8 байт раніше (за адресою `+8`
  замість `+16`) — це була помилка; вона довго лишалась непоміченою, бо робота зі
  шрифтами все одно давала робочий результат (див. нижче чому), але не копіюй старі числа
  з пам'яті.**
- Для чанка `SDAT` (нестиснутого) сирий payload починається за зміщенням **64** (відносно
  тегу чанка) і триває до кінця чанка — ця частина старих чисел (64-байтний оверхед, 8128
  корисних байт з 8192-байтного чанка) була правильною і збігається з
  `_SDAT_PAYLOAD_PREFIX` у `lotr_scw_tool.py`.
- Чанки `Rdat` — **стиснуті** і ніде не використовуються в пайплайні шрифтів/subT, описаному
  в цьому документі (лише "чиста" багатомовна майстер-інсталяція використовує `Rdat` — див.
  `TODO_MASTER_SUBT_DECOMPRESSION.md`). Ресурси шрифтів і `subT` у регіональній
  одномовній інсталяції, з якою велась уся робота тут, — `SDAT` (нестиснуті).
- Чанки `LLIF` (=FILL) вирівнюють до меж по 65536 байт (підтверджено побайтово і в
  `GlobScen.scw`, і в аудіо `.scw`-файлах).
- Щоб знайти корисні діапазони байтів ресурсу: знайти його `SHDR`-чанк (за полем `ext`),
  далі обходити чанки починаючи з місця, де цей `SHDR`-чанк закінчується, збираючи
  сегменти `(payload_start, payload_len)`, поки не покриється заявлений `decompLen`. Файли
  шрифтів, текст `subT` тощо — усі інжектуються за цією ж логікою "сегментованого запису"
  (заміна того самого розміру або з перевіркою місткості, доповнення нулями якщо коротше).

**Використовуй `lotr_scw_tool.py` напряму замість повторного виведення всього цього** —
`list_resources()` / `read_resource()` / `write_resource()` реалізують саме описане вище,
перевірено від початку до кінця (побайтовий round-trip проти вже відомих правильних
файлів). Чому пайплайн шрифтів все одно працював попри баг зі зміщенням вище: ті чорнові
скрипти, найімовірніше, знаходили початок payload ресурсу емпірично (скануючи на
розпізнаваний вміст, напр. сигнатуру `FNTS`), а не обчислювали його чисто з розкладки полів
заголовка, що й обходило баг — але це також означає, що їхня точна внутрішня логіка ніколи
не була повністю зафіксована письмово до цього перепису. Будь-яку майбутню роботу зі
шрифтами варто переводити на `read_resource()`/`write_resource()` з `lotr_scw_tool.py`,
а не відновлювати старий підхід.

## 2. Формат файлу `.font` (FNTS) — повністю реверс-інжинирено

Реверс-інжинирено через **вихідний код** реального робочого GUI-інструменту:
`bartlomiejduda/EA-Font-Manager` (GitHub), а також пакет `reversebox` з PyPI, від якого він
залежить для декодування пікселів (`pip install reversebox`). Це був ключовий прорив —
довіряти вихідному коду реального інструменту замість того щоб продовжувати вгадувати.

### 2.1 Заголовок файлу (32 байти, little-endian)
```
sign            4 байти  "FNTS"
total_f_size    u32
file_version    u16      (200 у всіх наших файлах)
num_of_characters u16    (288 у всіх наших файлах)
font_flags      u32
center_x        u8
center_y        u8
ascent          u8
descent         u8
char_info_offset u32     (=32, тобто одразу після цього заголовка)
kerning_table_offset u32 (= точний кінець даних пікселів/зображення)
shape_header_offset u32  (= char_info_offset + num_of_characters*12)
```

### 2.2 Таблиця символів
Починається з `char_info_offset` (32), по 12 байт (`Character12Entry`) на символ, всього
`num_of_characters` записів (288). Формат структури `"<HBBHHBBBB"`:
```
code      u16
width     u8
height    u8
x         u16   (позиція в атласі пікселів)
y         u16
advance   u8
x_offset  u8
y_offset  u8
num_kern  u8
```
**Це місяцями хибно читалось як `"<HBBHHHH"`** (2×u16 замість 4×u8 для останніх полів) —
саме цей баг пояснював величезну кількість заплутаних калібрувальних шумів раніше.
Використовуй структуру з 12 байт / 9 полів вище — вона підтверджено правильна.

Таблиця має **два логічні блоки**:
- **Основний блок**: індекси `0..223`, коди `32..255` послідовно (`index = code-32`).
- **"Дубль"-блок**: індекси `224..287`, які *дзеркалять* коди `192..255` вдруге, але з
  **фіксованим, завищеним обмежувальним боксом** (спостережувана висота — стабільно
  **93px** для кожного запису в цьому блоці, незалежно від файлу). Реальні пікселі букви
  всередині цього боксу — звичайного розміру (напр. реальна висота ~22px), з великими
  полями зверху/знизу — підтверджено скануванням ненульових рядків всередині боксу.
- **Побудова `by_code` (код → запис) обов'язково потребує дедуплікації**: наївний
  `{e["code"]: e for e in entries}` дозволяє *останньому* обробленому запису перемогти —
  тобто завищений запис дубль-блоку мовчки перезаписує основний для кожного коду
  192-255. Завжди будуй словник так, щоб перемагав **основний** (index < 224) запис для
  прямих пошуків, наприклад:
  ```python
  by_code = {}
  for i, e in enumerate(entries):
      if not (e["code"] in by_code and i >= 224):
          by_code[e["code"]] = e
  ```
- **Однак — критична знахідка —** щонайменше для одного файлу шрифту
  (`Unnamed File 000001.font`, найбільший/"головний") записи **основного блоку** для
  кількох кириличних кодів самі по собі пошкоджені/неправильні (залишки латинських/
  англійських гліфів, напр. код 195 "Г" в основному слоті насправді містить форму "Ã",
  код 227 "г" в основному слоті містить цифру "3"). **Дубль-блок** надійно містив
  *правильний* гліф для тих самих кодів. **При використанні існуючої кириличної букви як
  донора/джерела для копіювання чи дзеркалювання, віддавай перевагу запису з дубль-блоку,
  обрізаному до реального обмежувального боксу** (шукати щільний прямокутник ненульових
  пікселів всередині завищеного боксу — див. §4). **Не довіряй** основному блоку сліпо як
  джерелу — завжди перевіряй візуально.

### 2.3 Формат пікселів — `ALPHA4_17X` (entry_type 122 / 0x7A)
**Підтверджено через `reversebox/image/image_decoder.py`, `_decode_generic` для
`bits_per_pixel==4`, `image_endianess="big"`** (збігається з
`bartlomiejduda/EA-Font-Manager`, `src/EA_Font/ea_image_decoder.py`, гілка для
entry_type 122, яка викликає `decode_image(image_data, width, height,
ImageFormats.ALPHA4_17X, image_endianess="big")` напряму — **жодного свізлінгу не
застосовується** для цього типу запису; гіпотеза PS2-свізлу була перевірена і остаточно
відкинута).

- 4 біти на піксель, тільки альфа (RGB завжди білий 0xFF; альфа = ніббл × 17).
- **2 пікселі упаковані в 1 байт, порядок ніблів big-endian**: перший/лівий піксель =
  **старший** ніббл, другий/правий = **молодший** ніббл.
- Декодування: `pixel(i) = (byte>>4)&0xF`, `pixel(i+1) = byte&0xF`, послідовне читання,
  рядок за рядком (`byte_width = справжня_ширина_пікселів / 2`).
- Перевірено піксель-у-піксель проти реального експорту з GUI-інструменту EA Font
  Manager.

**Де насправді починаються дані пікселів (це був реальний, багатомісячний баг):**
Існує **16-байтний саб-заголовок "shape/image directory entry"** за
`shape_header_offset`, *окремо* від таблиці символів, який спочатку взагалі не
враховувався:
```
record_id        u8     (122 = ALPHA4_16X/17X для наших файлів)
size_of_the_block u24   (little-endian, 3 байти, зазвичай 0 у наших файлах)
width             u16   (заявлена повна ширина атласу, напр. 512 або 1024)
height            u16   (заявлена повна висота атласу)
center_x          s16
center_y          s16
[ще 2 упакованих поля, не використовуються для наших цілей]
```
**Справжні дані пікселів починаються з `shape_header_offset + 16`**, і закінчуються на
`kerning_table_offset` (точно, з 32-байтного заголовка файлу — без жодних підгонок).
Розмір байтів зображення **повинен** дорівнювати
`заявлена_ширина * заявлена_висота / 2` (4bpp) — це варто перевіряти assert-ом.

**Місяцями** робочі скрипти використовували **захардкоджений**
`table_end = 32 + 224*12 = 2720` як офсет початку даних пікселів — це **неправильно з
двох причин**: (а) припускає лише 224 записи замість справжніх 288, і (б) не пропускає
16-байтний saB-заголовок shape. Фактична помилка полягала в тому, що нові пікселі букви
записувались приблизно на 784 байти РАНІШЕ у файлі, ніж там, де гра їх реально читає —
тобто гліф існував у файлі, навіть був видимий у самоузгоджених перевірочних кропах
(бо перевірка використовувала *той самий* неправильний офсет), але гра читала інший,
все ще порожній регіон. **Це повністю пояснює довгостроковий симптом "гра малює символ,
але він порожній".**

**Правильна, актуальна формула (перевірено робочою в грі станом на варіант 20/21):**
```python
pixel_start = shape_header_offset + 16
pixel_end   = kerning_table_offset       # з 32-байтного заголовка файлу, точно
byte_width  = declared_width // 2
# image_bytes = data[pixel_start:pixel_end]; len(image_bytes) == declared_width*declared_height//2
```

### 2.4 Таблиця кернінгу
Після даних пікселів, за `kerning_table_offset`. Записи —
`(char1: u16, char2: u16, delta: i8, padding: 3×0x00)` = 8 байт кожен. Не модифікується в
жодній з цих робіт; читається лише щоб знайти, де закінчується регіон пікселів.

## 3. Знахідка щодо кодової сторінки cp1251 (усуває проблему "жертовної букви")

Коди `165, 170, 175, 178, 179, 180, 186, 191` — це **не довільні "жертовні" слоти** —
це **реальні, стандартні позиції кодової сторінки Windows-1251** для специфічно
українських букв Ґ/ґ, Є/є, Ї/ї, І/і:
```python
>>> "ҐЄЇІіґєї".encode("cp1251")
```
дає точно `0xA5(165)=Ґ, 0xAA(170)=Є, 0xAF(175)=Ї, 0xB2(178)=І, 0xB3(179)=і,
0xB4(180)=ґ, 0xBA(186)=є, 0xBF(191)=ї`. Це означає, що текст `subT` можна кодувати
**простим, немодифікованим `str.encode("cp1251")`** — жодна таблиця замін символів не
потрібна для цих букв; cp1251 вже розміщує їх саме на тих кодах, для яких ми патчимо
гліфи. (Раніший, вже відкинутий підхід замінював ці букви на візуально схожі російські
букви в тексті — цей підхід explicit відкинутий власником проєкту і ніколи не має
повертатись.)

Базовий кириличний блок `192-255` (32 великі + 32 малі, стандартний російський
алфавітний порядок за cp1251) — **єдиний** діапазон кодів, підтверджено коректно
рендерений в грі без змін. Діапазони `128-159` (керуючі символи C1) та
`176-223`/інші DOS/латинські-залишкові діапазони були протестовані і **не** рендерять
новий вміст надійно.

## 4. Техніки редагування гліфів, які працюють (у порядку переваги)

Усі вони перевірені прямим переглядом пікселів (невеликі кропи з невеликим полем в
кілька пікселів, переглянуті при 8-10x збільшенні) **перед** інжекцією в гру, а потім
підтверджені в грі скріншотами. Усі керуються **тими самими** офсетами з §2.3 —
ніколи захардкодженими константами.

1. **Пряме копіювання 1:1 з перевіреної букви того самого регістру.** Найкраще, коли
   українська буква візуально ідентична або майже ідентична існуючій правильній.
   - `Ґ (165) ← Г (195)`, `ґ (180) ← г (227)` — буквальні копії.
   - `І (178) ← латинська 'i' (105)`, `і (179) ← латинська 'i' (105)` — за явною
     інструкцією, і велика, і мала українська "крапкова і" використовують **той самий**
     маленький гліф, що й мала латинська `i` (це відповідає реальній українській
     типографії, де велика І не має окремої більшої форми).
   - **Коли код-донор лежить у 192-255, брати джерело з дубль-блоку (обрізане до реальних
     меж), а не сліпо з основного блоку** — див. знахідку про пошкодження у §2.2.
   - Після копіювання пікселів **перерахуй** `advance`/`x_offset`/`y_offset`, 
     використовуючи власне калібрування регістру призначення (див. §5) — **не**
     використовуй сирі метрики донора буквально, якщо донор прийшов з дубль-блоку (його
     метрики описують завищений бокс, а не обрізаний гліф).

2. **Дзеркальне відображення існуючого гліфа по горизонталі.** Використано для
   `Є (170) ← Э (221)` дзеркально зліва направо (кирилична Є виглядає як
   дзеркальна/перевернута форма "Ɛ", схожа на Э). Те саме правило обрізки+перекалібрування
   застосовується, коли джерело лежить у 192-255.

3. **Зменшення вже виправленого гліфа для іншого регістру.** `є (186)` побудовано,
   взявши бітмап *вже виправленої* `Є (170)` і зменшивши його за співвідношенням
   `x_height/cap_height` (PIL `Image.resize(..., Image.LANCZOS)`), потім
   переквантувавши 8-бітну альфу назад у 4-бітну. Корисно, коли немає чистого донора
   для малої літери, але є чистий для великої.

4. **Рендер з нуля з TTF (Open Sans)** — останній засіб, все ще використовується для
   `Ї (175)` / `ї (191)` станом на останню робочу версію. Це техніка, найбільш схильна
   до бага "буква виглядає замалою" (див. §5) через те, як обчислюється цільова висота
   для гліфів з діакритикою.

**Розміщення:** нові/модифіковані гліфи розміщуються у справді вільному просторі *в
межах вже заявлених розмірів атласу* (`declared_width × declared_height` з §2.3), нижче
найнижчого реального вмісту (`max(e.y+e.h for e in entries if e.w>0)`), у простому
пакуванні зліва-направо з переносом на новий рядок. Це означає, що **розмір файлу ніколи
не потрібно змінювати** — підтверджено: кожен перезібраний `.font`-файл залишається
байт-у-байт того ж розміру, що й оригінал, що повністю усуває будь-який ризик щодо
обмежень місткості чанків `.scw`. У кожному перевіреному файлі є велика кількість
справді вільного простору (сотні невикористаних рядків) — ніколи не потрібно
розглядати дописування за межі заявленого полотна.

## 5. Калібрування метрик (advance / x_offset / y_offset)

Для будь-якого нового/зміненого гліфа не використовуй сирі метрики донора наосліп.
Натомість:
```python
def calibrate(by_code, code_range):
    # code_range = range(65,91) для великого регістру (латинські A-Z),
    #              range(97,123) для малого регістру (латинські a-z)
    adv_delta = mode(entry.advance - entry.w for entry in code_range)
    xoff_mode = mode(entry.x_offset for entry in code_range)
    yref      = mode((signed(entry.y_offset) + entry.h) for entry in code_range)
    return adv_delta, xoff_mode, yref

# потім, для нового гліфа шириною gw/висотою gh:
advance   = clamp(gw + adv_delta, 0, 255)
x_offset  = xoff_mode
y_offset  = (yref - gh) % 256   # unsigned-обгортання
```
Використовуй калібрування **великого регістру** (з латинських `A-Z`, коди 65-90) для
цілей великого кириличного регістру, калібрування **малого регістру** (з латинських
`a-z`, коди 97-122) для цілей малого регістру. `cap_h = by_code[65].height`,
`x_h = by_code[97].height` — цільові висоти рендеру при рендерингу з нуля з TTF.

### Відомий відкритий баг: проблема "замалої букви"
При рендерингу з нуля з TTF (техніка №4 в §4) для символу **з діакритикою** (крапка,
гачок, бревіс — напр. Ґ, І, Ї, ґ, і, ї), *весь* обмежувальний бокс гліфа (тіло букви +
діакритика) масштабується під цільову висоту (`cap_h`/`x_h`), що візуально зменшує саме
тіло букви, щоб звільнити місце під діакритику зверху. Букви **без** діакритики (Є, є)
цієї проблеми не показують. **Саме тому техніку №4 було відкинуто на користь №1-3, де
тільки можливо** — Ї/ї — єдині дві букви, що досі використовують її станом на останню
робочу версію, і вони досі показують цей артефакт "замалості" в грі. **Наступний крок
для того, хто продовжить цю роботу: дати Ї/ї те саме лікування копіювання/
дзеркалювання/зменшення, що й іншим шести буквам, беручи джерело з існуючого
крапкового/бревісного латинського чи кириличного гліфа замість повторного рендерингу з
Open Sans.**

## 6. Практичний пайплайн / як перезібрати

1. Завантажуй кожен з 8 файлів `.font` заново з **чистої (pristine)** папки RU-інсталяції
   (`C:\Users\UserM\Documents\lotr\*.font` у робочій сесії — відтвори еквівалентну чисту
   копію, якщо їх немає) — ніколи не ланцюжкуй зміни поверх виводу попереднього варіанту.
2. На файл: прочитай заголовок (§2.1), побудуй `entries`/`by_code`/`by_code_dup` (§2.2),
   застосуй зміни гліфів (§4) з калібруванням (§5), запиши назад — той самий розмір
   файлу, ті самі значення заголовка окрім торкнутих рядків таблиці символів.
3. Збери `subT` з українського тексту перекладу (`key = value` на рядок), використовуючи
   **просте `str.encode("cp1251")`**, без таблиці замін (§3). Бінарний макет `subT`:
   36-байтний заголовок (копіюється дослівно з вихідного файлу, а не переобчислюється) +
   `pair_count*2` little-endian u32 офсетів (пари key_offset, value_offset, відносно
   бази блоба) + сам блоб (`key\0value\0` повторюється, cp1251). Тепер весь цей крок —
   це `build_subt()` / `inject_text_into_subt()` з `lotr_scw_tool.py` — використовуй їх
   замість повторного виведення; дивись докстринг того файлу та
   `extract_subt_to_text()`/`parse_text_pairs()` щодо формату `key = value`, який він
   читає й пише.
4. Інжектуй усі 8 шрифтів + `subT` у свіжу копію чистого RU `GlobScen.scw`,
   використовуючи логіку сегментованого запису з §1. `list_resources()` з
   `lotr_scw_tool.py` знаходить позицію `SHDR` кожного ресурсу автоматично (за полем
   `ext`) — не треба шукати офсети емпірично для кожного файлу, як доводилось раніше в
   цій сесії. `write_resource()` сам робить перезапис "той самий розмір / з перевіркою
   місткості".
5. **Завжди роби візуальну перевірку перед доставкою**: вирізай кілька відомо-правильних
   еталонних гліфів (латинські A/a, кириличні А/а) **і** кожен новоторкнутий гліф, з
   невеликим полем (3-5px) навколо кожного, при 8-10x збільшенні, з **фінального
   збереженого файлу**, використовуючи ту саму математику офсетів, що й шлях запису. Це
   постійна політика проєкту після раннішої катастрофічної доставки (скріншот показав
   гігантські пошкоджені смуги), яка дійшла до користувача без цієї перевірки.
6. Копіюй зібраний `GlobScen_UA.scw` у
   `C:\Program Files (x86)\Return of the King\Data\Game\GlobScen.scw` для тестування
   користувачем у грі.

## 7. Що досі не працює / відкриті питання

- **Ї / ї** досі використовують техніку TTF-рендеру і показують артефакт "замалості" в
  грі (§5). Потребують лікування копіюванням/дзеркалюванням/зменшенням замість цього.
- **Проблема 33-ї української букви**: якщо майбутня задача захоче перевпорядкувати
  **весь** блок 192-255 в український алфавітний порядок (на відміну від поточного
  мінімального патчу, що торкається лише 8 кодів), є **жорсткий конфлікт місткості**:
  в українському алфавіті 33 букви, а в основному блоці лише 32 слоти (192-223 великі /
  224-255 малі). Це було позначено, але ніколи не вирішено — обговорювані, але не
  реалізовані рішення: використати один з вже торкнутих слотів типу 165/170/175/178 для
  Я/я, або погодитись на пропуск однієї букви для скороченого тесту. **Поточний
  доставлений підхід повністю уникає цього**, патчаючи лише 8 конкретних кодів і
  залишаючи решту 192-255 як стандартну cp1251 російсько-порядкову кирилицю (що також
  валідне для української мови для тих спільних букв).
- **Кириличний "дубль-блок" (індекси 224-287, 93px-високі бокси)** — його реальне
  призначення в грі так і не було з'ясовано. Не використовується нічим у поточному
  підході, окрім як (підтверджено надійне) джерело-донор для кількох букв в одному
  конкретному файлі шрифту. В решті — повністю не торкається.
- Жодної спроби не було зроблено перекодувати `subT` для будь-якої іншої схеми, окрім
  простого cp1251 — якщо майбутня задача змінить, які коди представляють які букви
  (напр. вищезгадана ідея алфавітного перевпорядкування), крок кодування тексту `subT`
  в §6.3 потребуватиме кастомного посимвольного мапінгу замість `str.encode("cp1251")`.

## 8. Ключові зовнішні джерела, використані в роботі

- `bartlomiejduda/EA-Font-Manager` (GitHub) — GUI-інструмент, чий вихідний код був
  джерелом істини для всього формату `.font`. Клонуй і читай
  `src/EA_Font/ea_font_file.py` (парсинг заголовка/таблиці) та
  `src/EA_Font/ea_image_decoder.py` (диспетчеризація entry_type → декодування,
  підтверджує відсутність свізлу для типу 122).
- `reversebox` (пакет PyPI) — `pip install reversebox`. Використовується для
  `reversebox.image.image_decoder.ImageDecoder` (декодування пікселів ALPHA4_17X як
  джерело істини, підтверджує порядок ніблів) — **не використовуй**
  `reversebox.compression.compression_refpack` для чогось у пайплайні шрифтів; він був
  досліджений для *аудіо*-роботи і виявився нестабільним/ненадійним (див. окремий
  документ висновків по аудіо), але для шрифтів він взагалі не був потрібен, оскільки
  дані пікселів шрифту не стиснуті refpack-ом.
- **Game Extractor** (`GameExtractor.jar`, лежить у цьому репозиторії) — опенсорсний
  Java-інструмент; клас `org.watto.ge.plugin.archive.Plugin_SCW` — джерело істини для
  формату контейнера `.scw`, описаного в §1 і реалізованого в `lotr_scw_tool.py`.
  Декомпілюй його через [CFR](https://github.com/leibnitz27/cfr), якщо треба щось
  перевірити ще раз: `java -jar cfr.jar Plugin_SCW.class --outputdir out/` (спершу
  дістань `.class`-файл із джарки через `unzip`). Довіряй свіжій декомпіляції, а не
  нотаткам у цьому документі, якщо вони розійдуться.
- `lotr_scw_tool.py` (цей репозиторій) — фактична, перевірена реалізація всього з §1 і
  кроків збірки/інжекції `subT` з §6. Читай докстринг модуля для повного опису формату
  з точними зміщеннями байтів.
